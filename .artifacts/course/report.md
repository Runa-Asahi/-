实验项目：模拟即时通信系统实现

# 一、设计任务分析

## 1.1 任务背景与目标

QQ、微信、微博等服务各自独立提供功能，又互相辉映关联，需要整合为统一的立体社交软件平台。本设计以「模拟即时通信系统」为题，用 C++17 与面向对象方法实现该平台的模拟系统：既要逐条完成课程规定的功能要求，又要在类的划分、抽象与封装、多态运用、可扩展性与灵活性上达到课程要求的五个技术层次。

设计目标可归纳为三点。第一，用清晰的类层次表达「人—服务账号—订阅关系」这类现实概念，而不是把概念塞进少数几个大类。第二，把随平台而异的行为（群的加入方式、管理结构、子群能力）交给运行时多态处理，而不是写成一串分支判断。第三，让数据与行为的边界可验证——所有关键业务规则都在接口层完成校验，违反规则时立即抛出异常，而不是静默返回一个错误状态码。

# 二、设计方案

## 2.1 总体架构与依赖方向

系统按职责分为四层，依赖方向自上而下，下层不感知上层：

```
入口层      main.cpp（--demo 演示脚本）
应用服务层  AccountManagerFanLX · AccountSessionFanLX
            FriendServiceFanLX · GroupServiceFanLX
领域层      UserProfileFanLX · ServiceAccountFanLX · FriendDirectoryFanLX
            IdentityResolverFanLX · GroupFanLX · GroupMembershipFanLX
            GroupKeyFanLX · DiscussionGroupFanLX
            GroupPolicyFanLX（抽象基类）及两个派生策略
基础设施层  LruListFanLX · LruCacheFanLX · ArcCacheFanLX
            LfuFrequencyFanLX · MemoryPoolFanLX
```

分层带来的直接好处是替换成本低：基础设施层的缓存底座只依赖键、值与哈希器三个模板参数，与业务无关，因此可以独立测试，也可以在不改动业务代码的前提下更换淘汰策略。

## 2.3 类层次：继承、组合与泛型

第一，继承与多态。GroupPolicyFanLX 是抽象基类，声明四个纯虚函数：canCreateDiscussion 表示该平台是否允许建立子群，canAssignAdmin 表示是否支持管理员制度，mode 返回当前治理模式，name 返回平台名称；同时定义虚析构函数，保证经基类指针销毁派生对象不会造成资源泄漏。QQGroupPolicyFanLX 与 WechatGroupPolicyFanLX 以 final 派生并给出各自实现：QQ 允许子群、支持管理员；微信不允许子群、不提供有效管理员权限。调用方只持有 GroupPolicyFanLX 指针，具体行为在运行期按实际对象类型分派。

第二，组合与复用。FriendServiceFanLX 不继承任何类，而是以引用成员加组合成员的方式持有 FriendDirectoryFanLX、const AccountManagerFanLX 与 IdentityResolverFanLX，把「关系数据」「状态校验」「身份换算」三件事分开；GroupServiceFanLX 同理由 GroupFanLX、DiscussionGroupFanLX 与三个工作流容器组合而成。组合让数据的所有者与被使用者解耦，也便于在测试中替换。

第三，泛型容器。基础设施层全部用类模板实现：LruListFanLX、LruCacheFanLX、ArcCacheFanLX、LfuFrequencyFanLX 与 MemoryPoolFanLX 都以键值类型或元素类型为模板参数，同一份实现可服务于不同数据类型。

第四，值语义的小对象。UserProfileFanLX、ServiceAccountFanLX、GroupKeyFanLX、GroupMembershipFanLX 等用 struct 表达纯数据，只提供必要的行为，例如 GroupKeyFanLX 定义 operator== 并配套 GroupKeyHashFanLX 作为无序容器的哈希器。这样既保证了「(平台, 群号) 决定群身份」这一语义，又避免了为纯数据强加无意义的继承层次。

## 2.4 三层身份模型与接口分层

这是本设计在建模上最关键的一处决定。现实中有三类必须分开的概念：

| 概念 | 标识方式 | 说明 |
| --- | --- | --- |
| 人 | 不可变的内部 userId（如 U001） | 后台主键，用于聚合、统计与持久化 |
| 服务账号 | （平台, accountId） | QQ 号 / 微信号 / 微博号，是用户实际持有并用于登录的身份 |
| 服务开通记录 | （userId, 平台） | 记录用户是否开通了某平台的服务 |

由此推出接口分层。凡是「由某个已登录用户发起」的操作，一律经由登录会话 AccountSessionFanLX，签名中不出现 userId；操作对象中的另一方一律用平台账号（平台, accountId）指定。凡是配给、统计、持久化性质的操作（注册用户、建号、开通、按用户查询）保留在 AccountManagerFanLX 上，并显式以 userId 为参数。

这样做有三点收益。其一，符合现实语义：加好友用的是对方的 QQ 号而不是后台编号，登录用的是账号而不是用户编号。其二，内部主键不外泄，上层无法绕过业务规则去拼装内部键。其三，会话把「当前登录身份」变成可传递的对象，后续业务接口都以它为起点，参数反而更少。该分层在评审中被明确指出并落实：先取消以 userId 为参数的登录重载与绑定接口，再让好友域七个接口全部改为「发起方会话 + 对方平台账号」，最后补齐计划中的会话、自主开通、注销与错误分类。

## 2.5 关键设计决策

| 问题 | 方案 | 收益 |
| --- | --- | --- |
| 群的管理理念随平台而异，且要求「管理模式动态可变」同时成员数据不受伤害 | 把群的稳定身份（GroupKeyFanLX 与成员表）与治理行为（unique_ptr 持有的策略对象）分离，切换时只替换策略指针 | 成员、角色、加入顺序、子群与待处理工作流全部原位保留，切换前后可用快照逐项比对 |
| 2Q 与 ARC 两种缓存各自内置链表与哈希路由，逻辑重复 | 抽出公共底座 LruListFanLX，把哈希路由、链表次序与字节账目三者同步封装在一处 | 策略层只表达晋升与淘汰的意图，两种缓存实现明显缩短且行为一致 |
| 群成员需要可比较的加入信息，且重启后仍需可复现 | 用单调递增的 joinOrder 记录加入次序，并显式保存 nextJoinOrder | 排序结果确定；最后加入者退群后序号不被回收，跨重启比对才有意义 |
| 服务账号既是登录身份，就可能被重复注册 | addAccount 同时校验「同一用户同平台唯一」与「同一平台账号 ID 唯一」，并建立索引 | 登录可唯一定位账号；按账号 ID 的定位由线性扫描降为常数时间 |
| 失败原因需要被区分，而不是靠解析错误字符串 | 定义 ServiceNotSubscribedFanLX、ServiceNotConfirmedFanLX、SessionExpiredFanLX 三个异常类型，均继承 std::runtime_error | 调用方可按类型分支处理；既有的通用捕获仍然有效 |

## 2.6 对象之间的使用关系

账户域内部，AccountManagerFanLX 拥有全部账户数据，AccountSessionFanLX 只持有一个指向它的指针与三项身份信息，所有需要用户维度的操作都由会话转交管理器在内部完成。好友域中，FriendServiceFanLX 先向 AccountManagerFanLX 校验发起方与对端的可操作状态，再请 IdentityResolverFanLX 把平台账号换算成全局唯一的账号键，最后委托 FriendDirectoryFanLX 读写关系数据。群域中，GroupServiceFanLX 按群键取得 GroupFanLX，用 requireMode 与 requireManager 两个私有校验完成模式门控与权限门控，再调用群对象或工作流容器；策略对象只回答能力问题，不接触任何成员数据。

# 三、详细设计

## 3.1 账户域：资料、账号、开通与统一登录

### 3.1.1 数据组织

AccountManagerFanLX 内部维护六个容器与一个索引：usersFanLX 由 userId 映射到用户资料；accountsFanLX 由「userId|平台」映射到服务账号；accountIdIndexFanLX 由「平台|账号ID」映射到账号存储键；subscriptionsFanLX 保存已开通的「userId|平台」；bindingsFanLX 保存账号键之间的绑定关系；loggedInFanLX 保存当前处于登录态的账号键。

统一使用「userId|平台」作为存储键，依据是本域约定「一个用户在一个平台只持有一个账号」，该键正好是该平台账号的无损别名，因此既能表达订阅关系，又不引入第二套编号。索引 accountIdIndexFanLX 同时承担两项职责：平台内账号 ID 的唯一性校验，以及按账号 ID 的常数时间定位。

### 3.1.2 登录与统一登录

登录入口是 login(平台, 账号ID, confirmOthers)。它按平台与账号 ID 定位服务账号，取出归属用户，进入登录核心。未开通的服务不允许登录，直接抛出「未开通」类型的异常——系统不会因为用户登录就替他开通服务。confirmOthers 为假时只登录当前账号，为真时把该用户其余已开通平台按两条依据批量置为登录态。

第一条依据是「同号」：双方 sharedId 为真且账号 ID 完全相同，对应微博与 QQ 复用同一号码的情形。第二条依据是「显式绑定」：绑定表中存在成对记录，对应微信号码与 QQ 号码完全不同、但用户主动建立过绑定的情形。两条依据之外不再联动——「属于同一个人」本身不构成联动理由。

这一处是本设计修正过的地方。最初的实现以「同一个用户」为依据做键前缀匹配，结果是登录 QQ 会把该用户所有已开通平台一并登录；这与「微信号与 QQ 号本来就是两个独立账号」的现实不符，也使 sharedId 与绑定表双双成为只写不读的字段。改为两条依据后，两个字段都成为真实读者，联动行为也有了可解释的理由。

### 3.1.3 登录会话与前端身份

AccountSessionFanLX 由登录成功时签发，对外只暴露 service 与 accountId 两项信息，以及 isLoggedIn 用于判断会话是否仍然有效。会话内部保存的归属 userId 是私有成员，本类不提供任何访问器，因此前端拿不到内部主键；需要用户维度的操作由会话在内部完成，例如 subscribeTo 负责自主开通、logoutAll 负责平台注销。

会话不参与持久化，重启后自然失效，这与「重启不恢复旧会话」的要求一致。会话被注销后，isLoggedIn 返回假，好友域等使用方会抛出「已过期」类型的异常，而不是继续用一个失效身份操作。

### 3.1.4 绑定：建立、查询与解除

绑定以平台账号为参数：会话上的 bindTo 表示「把当前登录的这个账号绑定到另一个平台账号」，如「我在微信里绑定我的 QQ 号」；解除用 unbindFrom，查询用 boundAccounts 或管理器上的 isBound 与 bindingsOf。

归属校验在内部完成：两个账号必须属于同一内部用户，否则一律拒绝。这保证了「不能输入任意 QQ 号就把别人的账号绑到自己名下」这一约束。绑定记录是双向判定的，解绑时两个方向都会被尝试删除，因此解绑对调用方的书写方向不敏感；解绑后该关系不再参与统一登录联动。

### 3.1.5 自主开通、注销与错误分类

开通服务有两条路径。后端配给用 subscribe，供数据初始化与测试使用；用户自主开通用会话上的 subscribeTo，它在内部把请求落到本人名下，登录本身绝不会替用户开通未开通的服务。

注销分为两级：logout 只退出当前平台，其他平台不受影响；logoutAll 退出本人的全部已登录平台，内部按归属用户清理，签名中不出现 userId。

失败原因用三个异常类型区分：未开通对应服务未订阅，未确认对应服务已开通但本次登录尚未确认进入，已过期对应会话已被注销。三者都继承 std::runtime_error，因此既有的通用捕获写法仍然有效。

## 3.2 好友域：关系维护、交集与跨服务推荐

关系存储用一张无向邻接表加一张细节表。邻接表把账号键映射到与之互为好友的账号键集合，添加与删除都双向登记，因此不存在单向关系的中间状态；细节表保存备注与标签，键由「主人 + 换行符 + 对方」构成，换行符保证不会与账号键中的分隔符冲突。细节表中的备注是单向的：主人给对方的备注写在自己的记录里，对方的视角不受影响，这一点在测试中有正反例覆盖。

身份换算由 IdentityResolverFanLX 承担，账号键格式为「userId|平台|账号ID」。解析器区分两种口径：前端口径由平台与账号 ID 拼出账号键，内部口径由归属用户与平台拼出账号键，供「同一用户的另一个平台账号」这类换算使用。内部主键只在解析器内部参与拼接与反解，不会流向调用方。

业务门面 FriendServiceFanLX 的七个接口都以「发起方会话 + 对方平台账号」为参数。添加、修改备注、删除三个写操作先校验发起方会话有效、再校验对端账号已建号、已开通且已确认登录；查询类接口要求会话有效。跨平台共同好友与好友推荐要求两个会话属于同一个人，否则拒绝——这保证了跨平台聚合的前提真实成立。

推荐逻辑先取出本人在来源平台的好友，逐个跳过自己、跳过在目标平台没有账号的人、跳过在目标平台已经是好友的人，并用集合去重，最后排序返回，因此推荐结果稳定可复现。

## 3.3 群域：差异化策略、权限矩阵与无损切换

群的标识由 GroupKeyFanLX 表达，即（平台, 群号）二元组，并配套 GroupKeyHashFanLX 作为哈希器。这样 QQ 的 1001 群与微信的 1001 群是两个互不影响的群对象，符合「每个微X功能已有 1001 至 1006 群号」的设定。

成员表保存 GroupMembershipFanLX，即角色与加入序号的组合，并单独维护 nextJoinOrder 计数器。加入序号只在真正插入成功时递增，重复请求不消耗序号；角色变更与策略切换都不重置加入信息，因此「按账号 ID 和加入时间规范化排序后比较」这一无损判定有可用的数据基础。

踢人权限矩阵由四条规则组成：任何人不能踢群主、普通成员没有踢人权、管理员不能踢同级管理员、不能踢自己。权限判定是策略感知的：管理员只有当所在平台支持管理员制度时才被视为有效管理员，因此微信模式下的管理员不会获得踢人权。

两种加入方式分别实现。QQ 群走申请审批流：提交申请只是登记待处理记录，不等于入群；审批必须先通过模式门控与权限门控，先入群再消费申请记录，保证分配失败时仍可重试，重复申请则不覆盖已有待处理记录。微信群走邀请确认流：邀请人必须是群成员，同一被邀请人最多一条待处理记录，被邀请人确认时系统会重新验证邀请人是否仍在群内，若已离群则清理该记录并拒绝。

子群只允许在支持子群的模式下建立与扩员，且子群成员必须是父群成员的子集；成员退群时服务层同步清理其在子群中的席位，并撤销其发出的全部待处理邀请，避免留下悬空引用。

群模式的无损切换是本模块的重点。切换只做一件事：替换 unique_ptr 持有的策略对象。成员表、加入序号、子群与三张工作流容器都不被触碰，因此成员、角色、加入顺序、子群与暂停中的工作流天然全部保留。判定无损用的是快照比对：群对象可以导出一份按账号 ID 排序的成员快照（含角色与加入序号），切换前后逐项比较即可证明数据未受伤害。这一设计的另一面是「休眠与恢复」语义自动成立：管理员角色从未被删除，其生效权限随当前策略重新计算，切回原模式即恢复；而被撤销、被踢或已退群的人不会因为切换而复活。

## 3.4 缓存系统：LRU 段底座、2Q、ARC 与 LFU

缓存模块的设计动机是课程要求的有界缓存与索引优化。最初的实现让 2Q 与 ARC 各自内置一套链表与哈希路由，同一逻辑写了两遍。后续重构把这段重复逻辑抽成公共底座 LruListFanLX：它在内部同时维护哈希路由（键到链表迭代器的映射）、链表次序（队首最新、队尾最久未用）与字节账目三者，并对外提供定位、读取、入队首、刷新为最近使用、整体取出、淘汰队尾、按容量裁剪等操作。底座中最关键的约定是「整体取出」操作的执行顺序：先摘除路由，再搬出内容，最后销毁结点，保证任何时刻三者都保持一致。

在底座之上，2Q 缓存把容量切成约一比三的两段：新数据先进缓冲段，在缓冲段中被访问达到阈值次数后整条晋升到主段队首；两段各自有独立的条目数与字节数上限，超限立即裁剪。ARC 缓存进一步引入四个段：L1 与 L2 存放数据，B1 与 B2 是不占字节的幽灵段，只记录被淘汰键在淘汰时刻的频率快照。命中幽灵段说明「容量偏小」，于是自适应参数加一，反之命中另一幽灵段则减一，缓存据此动态调整 L1 的目标大小。这样既保留了 ARC 对访问模式的适应性，又用频率快照补足了对热点数据的判断。

频次控制器 LfuFrequencyFanLX 是独立组件而非缓存：它增量维护键的总访问次数，因此求平均访问次数是常数时间操作；当平均次数超过阈值时对全体计数做一次衰减，避免历史访问永远压过近期行为。ARC 通过组合复用它，而不是把频次逻辑再写一遍。

## 3.5 对象内存池

MemoryPoolFanLX 用两条链表管理内存：已申请的大块内存在一条链表上，块内切分出的空闲结点在另一条空闲链表上。申请对象时从空闲链表头部取结点，用定位 new 在结点存储区直接构造；释放时先显式调用析构函数，再把结点归还空闲链表头部。这样频繁创建销毁的小对象不必反复走系统分配器。结点用 alignas 保证对齐，析构时沿块链表统一回收全部内存，不需要逐个释放。

# 四、总结与体会

## 4.1 程序的优点

其一，类的职责边界清晰。账户、好友、群三个领域各有自己的存储类、解析类与门面类，基础设施层的缓存与内存池完全不依赖业务类型，因此可以独立测试与独立替换。「目录负责存、解析器负责换算、门面负责校验」这一分工，使每一处改动的影响范围都可预期。

其二，多态用得实在。群平台差异与群模式切换都建立在同一个抽象基类之上，切换只需替换策略对象，业务代码中没有一处按平台分支的 if 判断。这既是课程「抽象、封装层次」与「面向对象层次」的直接体现，也让「成员数据不受伤害」这一要求得到了结构性的保证，而不是靠小心翼翼的手工搬运。

其三，业务规则集中在接口层。重复注册、账号不存在、服务未开通、绑定他人账号、越权踢人、群主直接退群等违规情形都以异常形式立即暴露，并带有可区分的类型。这样做的好处是问题在调用点就暴露，不会带着错误状态继续往下走。

## 4.2 不足与改进方向

最明显的不足是持久化尚未接入，程序目前是纯内存系统，重启即丢数据；与之配套的事务顺序、备份发布与故障恢复也只有设计而无实现。其次，缓存缺少实测数据，设计上讨论的收益尚无吞吐与命中率佐证。再次，跨服务推荐的依据需要与「共享 ID 或已验证绑定映射」的口径对齐。最后，交互式菜单与会话的逐项确认登录仍待补充，目前只有批量确认。

## 4.3 调试中的典型问题与解决

第一处是统一登录的判定依据。最初以「同一个用户」为依据，登录一个平台会把该用户全部已开通平台一起置为登录态。表面上看演示结果是「对的」，但它与「微信号和 QQ 号本来就是两个独立账号」这一现实相矛盾，也暴露出 sharedId 与绑定表虽然存在却从未被读取。解决方式是重新分析登录的语义：登录是对账号的操作而非对用户的操作，统一登录的依据只能是「同号」或「显式绑定」两类客观关系，并用测试把三条路径（同号联动、绑定联动、仅同人则不联动）逐条固定下来。

第二处是内部主键泄漏到接口签名。修正完登录之后发现，绑定接口与好友域的全部接口仍然以 userId 为参数。这说明问题不在单个函数，而在缺少一条明确的接口分层规则。解决方式是把「由已登录用户发起的操作」与「后台配给与统计操作」分开：前者一律走会话对象，后者才使用内部主键；会话把内部主键作为私有成员保存且不提供访问器。改造之后，绑定接口改为以平台账号为参数，归属校验移到内部完成，好友域七个接口也全部更换口径。

第三处是账号 ID 缺少唯一性约束。在把账号 ID 提升为登录身份之后才发现，两个用户完全可能注册同一个平台账号 ID，而登录需要一个能唯一定位账号的键。解决办法是在建号时同时校验两重唯一性并建立索引，顺带把按账号 ID 的定位从线性扫描改成常数时间——一个语义上的遗漏反而带来一处性能改进。

第四处是缓存模块的重复实现。2Q 与 ARC 各自维护链表与哈希路由，改动其中一处很容易忘记同步另一处。解决办法是先找出两者真正共用的部分（路由、次序、字节账目三者的同步），把它抽成底座并单独测试，策略层只保留「何时晋升、何时淘汰」的决策。重构后用同一批随机操作对重构前后的实现做差分对拍，确认行为完全一致才替换。

第五处是群模式切换可能破坏群身份。如果让群键随当前模式变化，切换就会导致群对象「换键」而在容器中丢失。解决办法是把「创建命名空间」与「当前治理模式」分成两个属性：群键中的模式在创建后永久冻结，当前模式由策略对象回答，容器定位与模式判定因此互不干扰。

## 4.4 对本次课程设计的认识

这次设计最大的收获是体会到「先想清楚概念之间的关系，再动手写类」。设计中最难的部分并不是算法，而是判断哪些概念应当分开：把「人」与「服务账号」分开、把「账号归属」与「登录状态」分开、把「群的稳定身份」与「群的管理理念」分开、把「前端身份」与「后台主键」分开——这四处分离一旦确定，后面的接口自然就顺了；反过来，凡是事后觉得别扭的地方，追根到底都是在建模阶段把两个概念混在了一起。

同时也认识到封装的价值不只在于「数据私有」，而在于让规则无法被绕过。当所有入口都经过同一层校验时，调用方即使不了解全部约束也不会破坏系统的一致性；而当内部主键可以直接出现在接口参数里时，调用方就获得了绕过规则拼装数据的能力。真正把封装做扎实，需要的是对「谁应该看到什么」有明确判断，并把它体现在类型和签名里，而不仅仅是把成员变量标成 private。

最后，测试在本设计中起到了设计工具的作用。多条重要修正都是先写出一条与直觉相冲突的断言，才发现原设计与现实语义不符。这让我理解了断言式测试的价值：它记录的不仅是「程序现在是什么行为」，更是「我认为它应该是什么行为」。
